### インメモリ用データモジュールの理解
* **AIにさせたこと:**
  - 「インメモリ用データモジュールとは何か」について説明を求めた
  - 実装計画で言及されていた `app/data/posts.server.ts` の役割と特徴を理解したい

* **利用の流れ:**
  1. 実装計画書を読んで、インメモリ用データモジュールについてわからない点があった
  2. AIに「インメモリ用データモジュールとは」と質問した
  3. AIから主な特徴、実装内容、使用目的について説明を受けた

* **人間のチェック観点:**
  - 説明内容が実装計画書と整合しているか確認
  - サーバー専用モジュール（`.server.ts`）の概念が理解できたか
  - インメモリデータの特性（再起動で消える）を把握できたか

* **学んだこと・メモ:**
  - **サーバー専用モジュール**: `.server.ts` 拡張子で、クライアントからは参照しない。サーバー側でのみ実行される。
  - **データストレージ**: データベースやファイルは使わない。サーバーのメモリ内（グローバル変数など）でデータを保持。サーバー再起動でデータは消える。
  - **実装内容**: `Post` 型を定義し、モジュールスコープに `let posts: Post[] = []` を保持。`getPosts()`, `getPost()`, `createPost()`, `deletePost()` などの `async` 関数をエクスポート。
  - **使用目的**: React Router の `loader` / `action` から呼び出し、記事データの CRUD 操作を提供。

  要約すると、データベースを使わずに、サーバーのメモリ上でブログの記事データを管理するモジュールです。開発・学習用途に適した簡易的な実装です。

### posts.server.tsの実装内容の理解確認
* **AIにさせたこと:**
  - `app/data/posts.server.ts`の各処理の流れについて自分の理解が正しいか判定してもらった
  - `Promise<Post[]>`の意味について説明を求めた
  - `slice()`と`clonePost`の役割の違いについて説明を求めた

* **利用の流れ:**
  1. `posts.server.ts`を実装した後、自分が理解した処理の流れを箇条書きでまとめた
  2. AIに理解が正しいか判定してもらい、不正確な部分を指摘してもらった
  3. `Promise<Post[]>`という型アノテーションの意味がわからなかったので説明を求めた
  4. `slice()`で配列をコピーしているのに`clonePost`でオブジェクトもクローンしている理由が理解できなかったため、役割の違いについて説明を求めた

* **人間のチェック観点:**
  - 指摘された不正確な理解を修正し、正確な処理フローを把握できたか
  - 非同期処理とPromiseの関係性を理解できたか
  - 浅いコピー（`slice()`）と深いコピー（`clonePost`）の違いを理解できたか

* **学んだこと・メモ:**
  - **Promise<Post[]>**: `async function`は自動的に返り値を`Promise`でラップする。`Promise<Post[]>`は「将来、`Post[]`型の配列を返す約束」を表す型。
  - **getPosts()の処理フロー**: `slice()`で配列をコピー → `sort()`でソート → `map(clonePost)`で各要素をクローン
  - **slice()の役割**: 配列レベルでの浅いコピー。元の配列の順序や長さへの変更を防ぐ。ただし配列内のオブジェクト自体は同じ参照を共有する。
  - **clonePost()の役割**: オブジェクトレベルでの深いコピー。各Postオブジェクト（特に`createdAt`のDate）を新しいオブジェクトとして作成し、返り値のオブジェクトを変更しても元の`posts`配列に影響しないようにする。
  - **両方必要な理由**: `slice()`だけでは配列内のオブジェクトが共有されてしまうため、`clonePost()`で各要素もクローンする必要がある。これにより、呼び出し側が結果を変更しても元のデータに影響しない。

### SSR/CSRの判定
* **AIにさせたこと:**
  - プロジェクト全体を確認し、画面描画がSSRかCSRかを根拠とともに判定してもらった

* **利用の流れ:**
  1. `react-router.config.ts`や`package.json`などをもとにレンダリング方式を知りたいという疑問を提示
  2. AIが設定値やサーバー用依存関係、`.server.ts`ファイルの存在などを参照してSSRであると結論付けた

* **人間のチェック観点:**
  - 指摘された設定値（`ssr: true`）が実際にファイルへ反映されているか
  - 依存関係やビルド成果物がSSR構成と整合しているか

* **学んだこと・メモ:**
  - React Router v7では`react-router.config.ts`がSSRを切り替える中心設定になる
  - `.server.ts`命名や`@react-router/node`依存がSSRの根拠として重要

### SSRレンダリングフローの整理
* **AIにさせたこと:**

* **利用の流れ:**
  1. SSR時の処理経路が把握できなかったため、起動コマンドからブラウザ表示までの全体像を質問
  2. AIが`build/server/index.js`の`handleRequest`や`ServerRouter`の動きを中心に、loader/actionとデータモジュールの呼び出し順を整理

* **人間のチェック観点:**
  - 説明された関数やファイルが実際に存在し、コードと一致しているか
  - loader/actionの呼び出し順が想定どおりか

* **学んだこと・メモ:**
  - `renderToPipeableStream`でHTMLをストリーミングする仕組みと、`@react-router/serve`がビルド済みサーバーコードを実行する流れ
  - ルート解決後に親→子順でloaderが実行される点
  - `Layout`→`App`→`Outlet`→各ルートコンポーネントのデータ受け渡しイメージ

### loader/actionのテスト仕様書作成
* **AIにさせたこと:**
  - `loader` および `action` 関数のテストコードを実装するための仕様書を作成してもらった
  - 各ルートファイル（`_index.tsx`, `posts.$postId.tsx`, `posts.new.tsx`）で定義されている `loader` / `action` のテストケースを網羅的に定義してもらった

* **利用の流れ:**
  1. テストコードを実装する前に、仕様書を作成してテスト方針を明確にしたいと考えた
  2. プロジェクト構造を確認し、既存の `loader` / `action` の実装内容を把握した
  3. AIにテスト仕様書の作成を依頼し、正常系・異常系のテストケース、テスト環境・ツール選定、実装ガイドラインを含む包括的な仕様書を生成してもらった
  4. 生成された仕様書を `docs/08_test_specification.md` として保存した

* **人間のチェック観点:**
  - 仕様書に記載されたテストケースが、実際の `loader` / `action` の実装と整合しているか確認
  - テスト対象の関数（`loader` 3つ、`action` 2つ）がすべてカバーされているか確認
  - 異常系のテストケース（エラーレスポンス、バリデーションエラーなど）が適切に網羅されているか確認
  - テストツールの選定（Vitest）がプロジェクト構成と整合しているか確認

* **学んだこと・メモ:**
  - **テストフレームワーク選定**: ViteプロジェクトではVitestが統合しやすく、TypeScriptのサポートも良好
  - **テスト対象の分離**: `loader` / `action` 関数はコンポーネントから分離して単体テストとして実装する
  - **テストケースの網羅性**: 正常系だけでなく、異常系（エラーケース、バリデーションエラーなど）も適切にテストする必要がある
  - **テストデータ管理**: テスト間での独立性を保つため、`beforeEach` / `afterEach` でデータを初期化・クリーンアップする
  - **エラーレスポンスの検証**: `throw new Response(...)` された場合の検証方法を理解した
  - **リダイレクトの検証**: `redirect()` のレスポンスステータスコードや `Location` ヘッダーの確認方法を理解した
  - 仕様書を作成することで、テスト実装前にテスト方針を明確にでき、実装時の迷いが減る
