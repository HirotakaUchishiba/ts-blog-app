# 08. テスト仕様書 (Test Specification)

## 1. 概要

このドキュメントは、React Router v7 の `loader` および `action` 関数のテストコードを実装するための仕様書です。各ルートモジュールで定義されている `loader` / `action` の動作を検証し、正常系・異常系の両方のケースをカバーします。

## 2. テスト環境・ツール選定

### 2.1. テストフレームワーク

* **Vitest**: Vite プロジェクトとの統合が容易で、高速な実行が可能。TypeScript のサポートも良好。
* **@testing-library/react**: React コンポーネントのテストに使用（必要に応じて）。
* **@react-router/node**: React Router のテストユーティリティ。

### 2.2. テスト対象の分離

* `loader` / `action` 関数は、コンポーネントから分離して単体テストとして実装する。
* データレイヤー（`app/data/posts.server.ts`）は、テスト内でモック化するか、またはテスト専用のインメモリデータとして扱う。

### 2.3. テストファイルの配置

各ルートファイルに対応するテストファイルを配置する。

```
app/routes/
  ├── _index.tsx
  ├── _index.test.tsx         # テストファイル
  ├── posts.$postId.tsx
  ├── posts.$postId.test.tsx  # テストファイル
  ├── posts.new.tsx
  └── posts.new.test.tsx      # テストファイル
```

## 3. テスト対象のloader/action一覧

### 3.1. 記事一覧ページ (`app/routes/_index.tsx`)

**関数**: `loader`
**役割**: 全記事を取得し、作成日時降順でソートして返す。

### 3.2. 記事詳細ページ (`app/routes/posts.$postId.tsx`)

**関数**: `loader`
**役割**: 指定された `postId` に一致する記事を取得する。

**関数**: `action`
**役割**: 指定された `postId` の記事を削除し、一覧ページへリダイレクトする。

### 3.3. 記事新規作成ページ (`app/routes/posts.new.tsx`)

**関数**: `action`
**役割**: フォームデータから記事を作成し、一覧ページへリダイレクトする。

## 4. テストケース仕様

### 4.1. `_index.tsx` の `loader` テスト

#### テストケース 1: 正常系 - 記事が存在する場合

* **前提条件**: インメモリに複数の記事が存在する。
* **期待結果**:
  - `loader` が正常に完了する。
  - 返却されるデータに `posts` 配列が含まれる。
  - `posts` 配列は作成日時降順でソートされている。
  - 各記事の `createdAt` が ISO 8601 形式の文字列（`toISOString()` の結果）として返される。

#### テストケース 2: 正常系 - 記事が存在しない場合

* **前提条件**: インメモリに記事が存在しない（空配列）。
* **期待結果**:
  - `loader` が正常に完了する。
  - 返却されるデータに `posts` 配列が含まれ、その長さが 0 である。

### 4.2. `posts.$postId.tsx` の `loader` テスト

#### テストケース 1: 正常系 - 記事が存在する場合

* **前提条件**: 指定された `postId` に一致する記事が存在する。
* **入力**: `params.postId` に有効な記事 ID を指定。
* **期待結果**:
  - `loader` が正常に完了する。
  - 返却されるデータに `post` オブジェクトが含まれる。
  - `post.id` が指定された `postId` と一致する。
  - `post.createdAt` が ISO 8601 形式の文字列として返される。

#### テストケース 2: 異常系 - 記事IDが未指定の場合

* **前提条件**: `params.postId` が `undefined` または空文字列。
* **期待結果**:
  - `loader` が `Response` を `throw` する。
  - レスポンスのステータスコードが `400` である。
  - レスポンスのステータステキストまたは本文に「記事IDが指定されていません。」が含まれる。

#### テストケース 3: 異常系 - 記事が存在しない場合

* **前提条件**: 指定された `postId` に一致する記事が存在しない。
* **入力**: `params.postId` に存在しない記事 ID を指定。
* **期待結果**:
  - `loader` が `Response` を `throw` する。
  - レスポンスのステータスコードが `404` である。
  - レスポンスのステータステキストまたは本文に「記事が見つかりません。」が含まれる。

### 4.3. `posts.$postId.tsx` の `action` テスト

#### テストケース 1: 正常系 - 記事の削除が成功する場合

* **前提条件**: 指定された `postId` に一致する記事が存在する。
* **入力**: `params.postId` に有効な記事 ID を指定。`request.method` が `"POST"`。
* **期待結果**:
  - `action` が `redirect("/")` を返す（または `redirect` レスポンス）。
  - データストアから該当記事が削除される。

#### テストケース 2: 異常系 - 記事IDが未指定の場合

* **前提条件**: `params.postId` が `undefined` または空文字列。
* **期待結果**:
  - `action` が `Response` を `throw` する。
  - レスポンスのステータスコードが `400` である。
  - レスポンスのステータステキストまたは本文に「記事IDが指定されていません。」が含まれる。

#### テストケース 3: 異常系 - 許可されていないHTTPメソッドの場合

* **前提条件**: `request.method` が `"POST"` 以外（例: `"GET"`, `"PUT"`）。
* **期待結果**:
  - `action` が `Response` を `throw` する。
  - レスポンスのステータスコードが `405` である。
  - レスポンスのステータステキストまたは本文に「許可されていないメソッドです。」が含まれる。

### 4.4. `posts.new.tsx` の `action` テスト

#### テストケース 1: 正常系 - 記事の作成が成功する場合

* **前提条件**: フォームデータに有効な `title` と `content` が含まれる。
* **入力**: `FormData` に `title`（空でない文字列）と `content`（空でない文字列）を含む。
* **期待結果**:
  - `action` が `redirect("/")` を返す（または `redirect` レスポンス）。
  - データストアに新しい記事が追加される。
  - 作成された記事の `title` と `content` が、入力された値と一致する。

#### テストケース 2: 異常系 - タイトルが未入力の場合

* **前提条件**: `FormData` の `title` が空文字列または未定義。
* **期待結果**:
  - `action` が `Response.json()` を返す（または JSON レスポンス）。
  - レスポンスのステータスコードが `400` である。
  - レスポンスの JSON に `errors.title` が含まれ、値が「タイトルを入力してください。」である。
  - レスポンスの JSON に `fields.title` が含まれ、入力された値（空文字列）が保持される。

#### テストケース 3: 異常系 - 本文が未入力の場合

* **前提条件**: `FormData` の `content` が空文字列または未定義。
* **期待結果**:
  - `action` が `Response.json()` を返す（または JSON レスポンス）。
  - レスポンスのステータスコードが `400` である。
  - レスポンスの JSON に `errors.content` が含まれ、値が「本文を入力してください。」である。
  - レスポンスの JSON に `fields.content` が含まれ、入力された値（空文字列）が保持される。

#### テストケース 4: 異常系 - タイトルと本文の両方が未入力の場合

* **前提条件**: `FormData` の `title` と `content` の両方が空文字列または未定義。
* **期待結果**:
  - `action` が `Response.json()` を返す（または JSON レスポンス）。
  - レスポンスのステータスコードが `400` である。
  - レスポンスの JSON に `errors.title` と `errors.content` の両方が含まれる。

#### テストケース 5: 正常系 - タイトルと本文の前後の空白がトリムされる場合

* **前提条件**: `FormData` の `title` や `content` に前後の空白文字が含まれる。
* **期待結果**:
  - `getString()` 関数により前後の空白がトリムされる。
  - トリム後の値が空でない場合、記事が正常に作成される。
  - トリム後の値が空になる場合、バリデーションエラーが返される。

## 5. テスト実装のガイドライン

### 5.1. テストデータの管理

* 各テストケースの実行前に、テスト用のインメモリデータを初期化する。
* テスト実行後は、データをクリーンアップする（必要に応じて）。
* `beforeEach` / `afterEach` フックを使用して、テスト間でのデータの独立性を保証する。

### 5.2. モックの使用方針

* `app/data/posts.server.ts` の関数は、直接テストするのではなく、テスト対象の `loader` / `action` から呼び出される形で統合テストとして実装する。
* もしくは、テスト環境で `posts.server.ts` をモック化し、各テストケースで期待される動作を制御する。

### 5.3. React Router のテストヘルパー

* `@react-router/node` のテストユーティリティを使用して、`loader` / `action` の引数（`Route.LoaderArgs`, `Route.ActionArgs`）を模擬する。
* `Request` オブジェクトや `FormData` を適切に構築して、`action` に渡す。

### 5.4. エラーレスポンスの検証

* `throw new Response(...)` された場合は、`expect(...).toThrow(Response)` や `expect(...).rejects.toThrow(Response)` を使用して検証する。
* レスポンスのステータスコードや本文を検証する。

### 5.5. リダイレクトの検証

* `redirect("/")` が返された場合、レスポンスのステータスコードが `302` または `307` であることを確認する。
* レスポンスヘッダーの `Location` が期待されるパスであることを確認する。

## 7. テスト品質基準

* **カバレッジ目標**: `loader` / `action` 関数のコードカバレッジを 80% 以上とする。
* **テストの独立性**: 各テストケースは、他のテストケースの実行結果に依存しない。
* **テストの明確性**: テスト名は、何をテストしているかが明確に分かるように記述する。
* **エッジケースの考慮**: 境界値や異常系のケースも適切にテストする。
